2. 코드 구조와 그렇게 짠 이유

  • 항목마다 구조(어떻게) → 이유(왜) → 근거(무엇을 보고) 순서
  • 「검수보고서 1-N」: 기존 파일에서 확인한 문제 번호

층 구조

run_config.py / run.py → cli.py     입구 (무엇을 할지)
        ↓
service.py                          흐름 (어떤 순서로, 어느 작업에)
        ↓
stages.py                           단계 실행 규칙 (건너뛰기, 저장, 멈춤)
        ↓
providers/*.py, secondary.py        사이트별 조회 규칙
        ↓
transport.py                        HTTP, 오류 분류

service.py → reporting.py → legacy/merge.py, export_selected.py   판정과 결과 파일

2-1. 입구는 하나, 기능은 층별로

구조
  • 실행: 기존처럼 파일 하나(run.py 또는 run_config.py)로 끝까지 진행
  • 내부: 흐름·실행 규칙·사이트 조회·통신을 파일별로 분리
이유
  • 한 번에 돌리는 입구: 원래 의도대로 유지
  • 조회 규칙 수정 시 해당 사이트 파일만 확인·시험
  • 사이트 추가 시 service 단계 한 줄 + providers 파일 하나
근거
  • 기존 run.py: 입구 + JS 호환 함수 + 통신 + 4개 사이트 조회 규칙 + 단계 실행 + CSV 변환이 한 파일 (검수보고서 1-9)

2-2. 조회 규칙은 원본 JS를 그대로 옮김

구조
  • providers/·secondary.py: collector.js·naver.js의 요청 주소·재시도·간격·판단 그대로
  • compat.py: 파이썬과 JS가 다른 부분(공백 문자, 반올림, 주소 인코딩, 객체 키 순서)을 JS 기준으로 맞춤
이유
  • 기존 결과와 같아야 새 코드로 교체 가능
  • 규칙까지 바꾸면 결과 차이의 원인(규칙 변경 vs 옮기기 실수) 구분 불가
근거
  • 시험 test_same_as_original_js: 원본 JS를 Node에서 같은 가짜 응답으로 실행 → A·B·C·NG·NV 결과와 요청 57개 목록 일치

2-3. 판정·결과 파일은 원본 코드를 별도 프로세스로 실행

구조
  • legacy/merge.py·common.py·build_outputs.py: 원본 유지, reporting.py가 별도 프로세스로 실행
  • 결과 파일: 새 어댑터 export_selected.py가 build_outputs 함수 호출
이유
  • 판정 규칙: 기존 작업(주안동·용현동 등)에서 이미 결과를 낸 코드 → 다시 짜면 결과 달라질 위험만 발생
  • 원본과 글자 단위 비교 가능 (tools/check_legacy.py)
  • 별도 프로세스 → API 키 환경변수 미전달
근거
  • merge.py 10줄: 「용현동·주안동 방식」 기록
  • build_outputs로 만든 HTML 카드: Codex 결과물과 글자 단위 일치
  • 대가: 판정 코드의 대기열이 JS 파일 형식 → 글자 위치로 읽음 (검수보고서 1-12) · 형식이 다르면 오류로 멈춤

2-4. 작업 ID와 SQLite 저장소로 이어 돌리기

구조
  • 작업 ID: CSV 내용·조회 범위·skip_geo·pipeline 코드·run_tag의 해시 24자
  • 조회 결과: work/jobs/<작업ID>/state.sqlite3에 건마다 즉시 저장
  • 같은 작업 동시 실행: OS 파일 잠금으로 차단
이유
  • 같은 조건 재실행 시 성공 건은 다시 호출 안 함 → 호출 한도·시간 절약
  • 코드 변경 시 새 작업 → 옛 코드 결과와 섞이지 않음
근거
  • 기존 run.py: 100건마다 저장 → 강제 종료 시 최대 99건 손실 (1-3)
  • 기존: 동시 실행 방지 없음 → 한쪽 결과 손실 가능 (1-11)
  • 시험: 재실행 시 호출 0회 · 조건·코드 변경 시 작업 ID 변경

2-5. 오류를 종류별로 나누고, 멈출 때를 정함

구조
응답오류 종류동작
401·403AuthError즉시 멈춤 (키·구독 문제)
429RateLimitError즉시 멈춤 (호출 한도)
리다이렉트, JSON 아님, 구조 다름UnexpectedResponse즉시 멈춤 (사이트 변경)
114On 차단 화면BlockedError즉시 멈춤 · 75분 뒤 재실행 안내
그 밖의 4xxRequestError그 건만 실패 · 재시도 없음
5xx, 네트워크 끊김RetryableError카카오 6번·네이버 4번 재시도 → 그 건만 실패
한 단계 실패 3건StageStopped그 단계 멈춤 (수집설정.toml max_errors)
이유
  • 「결과 없음」과 「응답 이상」 미구분 시 막힌 응답이 빈 결과로 저장 → 틀린 결과가 조용히 누적
  • 전부 실패할 상황에서 빨리 멈춤 → 호출 한도·시간 절약
근거
  • 기존 카카오 조회: 401만 멈춤, 403·429는 건마다 6번 재시도(약 38초) 후 다음 건물로 진행
  • 800건 기준 동시 4개로도 2시간 이상 헛돎 (검수보고서 1-2)

2-6. 네이버·114On 판정 파일에는 성공 건만 전달

구조
  • _export_ok_only: NG·NV·C.json에는 성공 행만 기록
  • A·B.json: 원본 형식대로 실패 행 포함
이유
  • merge.py: NG·C 파일에 건물 키가 있기만 하면 조회 완료로 간주 → 대기열에서 제외
  • 실패 행을 넘기면 그 건물은 재조회 불가
근거
  • merge.py 243·245줄 (검수보고서 1-1)
  • 시험 test_failed_geocode_is_retried_next_run: 한 건 실패 후 재실행 → 그 건만 재조회 · 옛 방식으로 되돌리면 시험 실패

2-7. API 키는 환경변수·.env에서만

구조
  • 키 출처: 환경변수 또는 .env (run.py·run_config.py 모두)
  • 키 요구 시점: 그 키가 필요한 단계 직전 (예: 이어 돌리기로 카카오 조회가 없으면 카카오 키 불필요)
  • 오류 메시지·응답 기록: <KAKAO_REST_KEY>처럼 가림
  • 결과 폴더: 엑셀·zip 내부까지 키 문자열 검사
이유
  • 결과 파일은 ERS·다른 사람에게 전달됨 → 키가 한 번 들어가면 회수 어려움
근거
  • 시험: 키 없을 때 필요한 단계에서만 멈춤 · 결과 폴더에 키를 넣으면 발견 · run.py의 .env 읽기

2-8. 설정 파일 두 개로 분리

구조
  • 조회설정.toml: 매번 수정 · CSV 경로, 구·동·등급 블록, 동시 조회 수, 114 범위
  • 수집설정.toml: 거의 수정 안 함 · 지역어 예외, 사이트 주소, 요청 간격, 오류 한도 · 기본값 = 원본 값
이유
  • 자주 고치는 파일과 규칙 값을 분리 → 실수로 건드릴 위험 감소
  • 사이트 주소·동별 예외 변경 시 코드 수정 불필요
  • 간격을 원래보다 줄이면 실행 시 차단 위험 경고
  • 수집설정.toml 값은 받은 조회 결과를 틀리게 만들지 않음 → 작업 ID에서 제외, summary.json에 기록
근거
  • 기존: 「주안동이면 관교 추가」·시도 이름·사이트 주소가 여러 파일에 박혀 있음 (검수보고서 1-5, 1-6, 1-13)
  • 설명서 개선안의 [[조회]]·구 = [...]: TOML 문법 오류 → 한글 이름은 따옴표 필요

2-9. 114On은 따로 실행

구조
  • 기본 조회가 끝난 작업에만 run114로 추가
  • 판정: 기본 결과 폴더(data)의 복사본 data114에서 수행
  • 코드 변경 시 거부
이유
  • 114On: 건당 4.5초 이상, 차단 위험 최대 → 기본 결과 먼저 확보 후 필요한 만큼만
  • 복사본에서 판정 → 기본 조회 결과 보존
근거
  • 원본: 브라우저의 114.co.kr 화면 안에서 따로 실행
  • 파이썬 직접 호출: 실제 확인 전 (검수보고서 2-2의 4번)
