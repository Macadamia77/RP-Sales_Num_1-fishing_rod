인천 건물정보 수집기 · 로직 설명서

콜리스트에서 건물명이나 대표번호가 빈 건물을 골라, 여러 사이트를 조회해 건물명·대표번호·대리 연락처를 채우는 코드가 어떻게 동작하는지 정리한 문서입니다. 재구조화와 회사 시스템(AWS) 병합을 앞두고 개발팀과 이야기할 때 쓰는 것을 목표로 했습니다.

핵심 요약

바쁘면 이 부분만 읽어도 됩니다. A부는 "무엇을 어디서 모아 어떤 조건으로 거르고 무엇을 고르는가"를, B부는 그 근거가 되는 코드 구조와 검수 결과를 다룹니다.

수집·정제 흐름 한 줄 요약

대상 주소 입력 → 카카오 주소검색으로 좌표·공식 건물명·주소 묶음 확보 → 주소 문자열로 카카오 장소검색(번호 대상이면 건물명으로도 재검색) → 주소가 같거나 200m 안인 장소만 남겨 장소 풀 구성 → 번호 대상이면 반경 300m 중개업소를 미리 8곳 확보 → 이름이 없으면 KB·집품에서 이름 보충 → 장소 풀에서 관리사무소 단어 + 이름 비교로 대표번호 선택 → 못 찾으면 건물 내 점포 2곳 + 주변 중개업소 3곳을 대리 연락처로 저장.

값을 정하는 규칙

  • 같은 건물 판단은 이름이 아니라 주소로 합니다. 표기를 통일(정규화)한 주소가 "같은지" 비교하고, "포함하는지"는 보지 않습니다.
  • 건물명: 카카오 공식 건물명 → 카카오 건물 장소 → 집품 → KB 단지명 순서로 처음 나온 것.
  • 대표번호: 주소가 같은 관리사무소이고 이름이 건물명과 비슷하면 1순위. 6가지 순위 중 가장 높은 1개를 고르고, 애매한 후보는 자동으로 넣지 않고 검수 후보로 보류합니다.
  • 대리 연락처: 대표번호를 끝내 못 찾았을 때만. 건물 내 점포는 업종 순위(중개사 > 헬스·노래방 > 병원·학원 > 식당 > 기타)로 2곳, 주변 중개업소는 가까운 순 3곳.

판단과 권고

  • 비공식 호출 3곳(KB부동산, 집품, 114On)은 예고 없이 막히거나 바뀔 수 있고 약관 문제가 있습니다. 법무 확인이 먼저입니다.
  • 재구조화: 사이트 조회 코드(pipeline/providers/)는 거의 그대로, 판정 코드(legacy/)는 "건물 1곳 → 결과" 함수로 다시, 실행 틀은 AWS 구조로 교체.
  • 데이터 보관: 장소 테이블 하나 + 건물-장소 연결 테이블에 원래 데이터를 저장하고 대리 연락처는 그 위에서 계산하는 방식을 권합니다. 부동산 DB는 공공데이터로 만듭니다.
  • 이번에 새로 확인한 코드 문제 2가지: 업종 분류가 "부동산"이 들어간 모든 장소(아파트·경비실 포함)를 공인중개사로 보고 맨 앞에 놓습니다. 카카오가 중개업소 거리를 빈칸으로 주면 0m로 저장됩니다.
가장 먼저 할 일이 코드는 가짜 API로만 검증됐습니다(검수보고서.md 2-2의 3번). 개발팀에 넘기기 전에 작은 동 하나로 실제 조회를 돌리고, 그 결과를 재구조화 후 비교할 정답 데이터로 고정해야 합니다.

카카오맵에서 선택된 건물명에 대표번호 없음"건물명에 번호가 있나"를 따로 묻는 단계는 없습니다. 장소 풀과 KB·114On에서 대표번호 후보를 6가지 순위로 찾아보고(P7), 하나도 남지 않으면 그때 대리 연락처를 만듭니다.
500m 내 부동산 목록 전체 수집300m, 카카오 분류 코드 AG2(중개업소)로 가까운 순 첫 15곳만 받아 전화 있는 8곳을 저장하고 최종 3곳을 씁니다. 대표번호를 찾았는지와 상관없이 번호 대상이면 미리 수집합니다(P4).
건물명 검색 시 나오는 모든 건물 정보 수집건물명이 아니라 주소 문자열로 장소검색을 합니다(검색어 최대 4개 × 최대 45건). 번호 대상이고 이름이 있을 때만 건물명과 건물명 관리사무소로 반경 1km를 추가 검색합니다(각 15건). 받은 것 중 주소가 같거나 200m 안인 장소만 남깁니다(P3).
부동산이나 중개소라는 단어가 들어간 목록 선별주변 부동산은 단어로 고르지 않습니다. 카카오 분류 코드가 이미 중개업소만 돌려줍니다. 건물 내 점포는 단어로 업종 순위를 매기는데, 공인중개|부동산중개|부동산이면 1순위입니다. "부동산"이 너무 넓어서 아파트·경비실도 1순위가 되는 문제가 있습니다(P8).
주소에 타겟 건물명이나 타겟 주소가 포함된 상가 선별건물명은 쓰지 않습니다. 장소의 도로명·지번을 정규화해 건물의 주소 묶음(건물이 가진 여러 주소)과 같은지 비교합니다. "포함"이 아니라 "같음"입니다(P3).

0먼저 바로잡을 점 3가지

개발팀과 이야기하기 전에 알고 있어야 할, 현재 코드에 대한 오해와 사실입니다.

① "100·200·300m 부동산"은 거리별로 나눠 찾는 게 아님

카카오에 "건물 좌표 기준 반경 300m 안 중개업소(분류 코드 AG2), 가까운 순"으로 한 번만 묻습니다. 페이지 지정이 없어 첫 페이지 15곳만 받습니다. 그중 전화번호가 있는 8곳을 저장하고, 최종 결과에는 건물 내 점포와 번호가 겹치지 않는 가까운 3곳을 넣습니다.

결과 파일에 보이는 100·200·300m 같은 숫자는 그 3곳의 실제 거리입니다(주변 부동산 · 87m 형태). 그래서 중개업소가 많은 곳에서는 3곳 모두 50m 안에 있을 수도 있습니다.

근거: pipeline/providers/kakao.py:187-189, legacy/merge.py:143-148, legacy/build_outputs.py의 proxy_rows

② "건물 내 점포"는 이미 수집하고 있음

주소가 같은 카카오 장소 중 관리사무소가 아닌 곳을 이미 "대리1~2 · 건물 내 점포"로 넣고 있습니다. 다만 결과 열에는 상위 2곳만 남습니다. 나머지 주소 일치 장소는 엑셀의 근거_주소일치장소 시트와 results.json에만 남습니다. 즉 건물 내 점포 데이터는 이미 흐르고 있고, 저장 방식만 정하면 됩니다.

③ 이 코드는 실제 API로 돌려 본 적이 없음

주소 묶음이 뭔가

  • 건물 하나가 땅 여러 필지에 걸쳐 있으면 지번이 여러 개입니다.
  • 모퉁이 건물은 도로명이 두 개일 수 있습니다.
  • 원본 CSV의 주소가 사이트에 등록된 주소와 다를 수 있습니다.

묶음에 들어가는 것

  1. 원본 CSV의 도로명과 지번
  2. 카카오 도로명 주소검색 첫 결과의 도로명과 지번
  3. 카카오 지번 주소검색 첫 결과의 도로명과 지번
  4. 네이버 지오코딩 결과의 도로명과 지번 (판정 단계에서 추가)

테스트 데이터의 실제 예입니다. 원본 지번은 관교동 13-11인데 카카오 지번검색은 같은 건물을 관교동 13-8로 돌려줍니다.

R = { 인천 미추홀구 주승로 247 }
J = { 인천 미추홀구 관교동 13-11, 인천 미추홀구 관교동 13-8 }

장소의 정규화된 도로명이 R에 있거나 정규화된 지번이 J에 있으면 주소 일치(건물 안 장소)입니다. 13-8로 등록된 관리사무소도 이 건물 것으로 잡힙니다. 주소가 다르면 건물 좌표에서 200m 안인 장소만 "근처 장소"로 남깁니다.

개발팀에 알려야 할 문제

주소 정규화 규칙이 네 벌 카카오·판정용 nr/nj(두 파일에 같은 이름으로 따로 있음), KB·집품용 short_a+sq(secondary.py), 114On용 k114R/k114J(one114.py)가 있습니다. 서로 조금씩 달라서 같은 주소를 단계마다 다르게 판단할 수 있습니다.

  • 그다음 건물명 재검색은 주소가 아니라 이름(동부아파트, 동부아파트 관리사무소)으로, 1페이지만, 좌표가 있으면 반경 1km로 검색합니다.

6KB부동산·집품 호출 방식

두 곳 모두 공식 API가 아니라, 웹사이트가 화면을 그리려고 자기 서버에 보내는 요청을 파이썬에서 똑같이 보내는 방식입니다.

"사이트 내부 호출"이 뭔가

  1. 웹사이트 화면은 뒤에서 자기 서버에 데이터를 요청하고, JSON으로 받아 화면에 그립니다.
  2. 브라우저 개발자도구(F12 → Network 탭)를 열고 사이트에서 검색해 보면 그때 나가는 요청 주소가 보입니다.
  3. 파이썬에서 그 주소로 똑같이 요청을 보내 JSON을 받습니다.
위험키도 로그인도 필요 없지만, 사이트가 주소나 응답 구조를 바꾸면 예고 없이 멈춥니다. 차단될 수 있고 약관 문제가 있습니다. 집품 사이트에는 "무단 크롤링 금지"가 적혀 있습니다.

요청을 보내는 방식 · pipeline/transport.py

  • 제한 시간 10초. 리다이렉트는 따라가지 않고 멈춥니다. JSON이 아니거나 구조가 다르면 멈춥니다.
  • KB·집품 코드에는 다시 시도하는 부분이 없습니다. 서버 오류가 나면 그 건물만 오류로 적고 3초 쉰 뒤 넘어갑니다.

  • 이전 버전은 run.py, prepare.py, collector.js, naver.js, merge.py, common.py, build_outputs.py였습니다.

9데이터 보관 방법 의견

세 안 중 하나를 그대로 고르기보다, 원래 데이터를 하나의 구조로 저장하고 피처는 그 위에서 계산하는 방식을 권합니다.

결론

  • 장소 테이블 하나와 건물-장소 연결 테이블에 원래 데이터를 저장하고, 건물의 대리1~5는 그 위에서 규칙으로 계산해 보여 줍니다.
  • 부동산 DB와 건물 내 점포 DB를 따로 만들지 않고, 같은 테이블 안에서 분류(중개업소인가)와 관계 종류(건물 안 / 근처)로 나눕니다.

순서

  1. 바로: 지금도 받는 데이터(주소가 같은 장소, 300m 중개업소)를 버리지 않고 저장합니다. 추가 호출이 없어 건물 내 점포 DB가 저절로 쌓입니다.
  2. 그다음: 개발자분 제안대로 부동산 DB를 지역 전체로 만듭니다. 카카오가 아니라 공공데이터로 만듭니다.
  3. 보류: 지역 전체 상가를 따로 긁어모으는 건물 내 점포 DB.

세 안 비교

근거

  1. 중개업소와 건물은 여러 대 여러 관계입니다. 지금은 번호 대상이면서 좌표가 있는 건물마다 카카오 중개업소 검색을 1번씩 합니다. 중구 대상 831건이면 최대 831번이고 정정, 같은 동 안에서는 300m 원이 거의 겹쳐 같은 업소를 반복해서 받습니다. 피처로만 저장하면 같은 정보가 수십 행에 중복되고, 고칠 때도 수십 행을 고쳐야 합니다.
  2. 피처는 규칙의 결과라서 원래 데이터가 없으면 다시 만들 수 없습니다. 지금도 가까운 15곳 중 8곳만 저장합니다. "500m로 넓히자", "휴대폰 번호는 빼자"를 하려면 전부 다시 호출해야 합니다.
  3. 카카오로 전체 부동산 DB를 만들기는 어렵습니다. 카카오 검색은 한 번에 최대 45곳까지만 줍니다. 지역을 잘게 쪼개 반복 호출해야 하고 빠진 곳을 확인하기 어렵습니다. 공공데이터(국토교통부 부동산중개업 정보, 시군구별 「중개업소 현황」)는 등록 중개업소 전체와 영업·휴업·폐업 상태를 줍니다. 유지보수는 한 달에 한 번 파일 갱신이 됩니다. 전화번호 포함 여부는 데이터셋마다 달라 확인이 필요하고, 없으면 상호+주소로 카카오를 검색해 번호만 붙입니다.
  4. 건물 내 점포는 이미 받고 있습니다. 저장만 하면 됩니다. 지역 전체를 따로 모으는 건 45곳 상한, 재조회 때만 갱신, 휴대폰 번호 혼입 문제가 있어 권하지 않습니다. 나중에 전체가 필요해지면 소상공인시장진흥공단 「상가(상권)정보」가 있습니다. 건물관리번호와 층 정보가 있고 분기마다 갱신되지만 전화번호는 없습니다.

의견 · 건물명이 들어 있는 상가만 남기는 방식

방향(건물 내 점포 DB)은 좋지만, 걸러내는 기준은 건물명이 아니라 주소로 해야 합니다.

  • 조회 대상 상당수가 애초에 건물명이 없는 건물입니다.
  • 카카오 장소 주소는 인천 미추홀구 주승로 247처럼 건물명이 없는 경우가 대부분이고, 상호에 건물명이 들어가는 경우도 드뭅니다.
  • 반대로 "푸르지오 부동산"은 길 건너 상가에 있을 수 있어 잘못 걸립니다.
  • 지금 코드처럼 정규화한 주소로 판단하는 게 더 정확하고, 건물관리번호를 쓰면 더 좋습니다.

의견 · "대표번호 없음 → 부동산 DB 조회" 트리거

동의합니다. 덧붙일 점입니다.

  • 트리거는 판정이 끝나 "대표번호 없음"이 확정된 뒤에 실행합니다.
  • 반경을 조회 조건으로 받으면 100·200·300m를 버튼에서 고를 수 있습니다. RDS PostgreSQL에 공간 검색 확장(PostGIS)을 붙이면 됩니다. 좌표가 없는 건물은 먼저 좌표를 채워야 합니다 보완.
  • 장소마다 마지막 확인 날짜를 저장해 오래된 번호는 전화 전에 다시 확인합니다.
  • 통화 결과(연결·부재·수신거부)를 장소에 붙이면 나중에 인사이트를 얻을 수 있습니다.

10개발팀 전달 요약

  1. 조회 모듈(pipeline/providers/)은 재사용하고, 판정(legacy/merge.py)은 "건물 1곳 → 결과" 함수로 다시 작성합니다. 두 벌인 규칙은 하나로 합칩니다.
  2. 재작성 전에 작은 동 하나로 실제 조회를 하고, 그 결과를 정답 데이터로 고정해 새 코드와 비교합니다.
  3. 결과는 문장이 아니라 출처 코드·우선순위·거리(m) 숫자로 저장합니다.
  4. 원래 응답(S3)과 장소·연결 테이블(RDS + PostGIS)을 저장하고, 대리 연락처는 그 위에서 계산합니다.
  5. 부동산 DB는 공공데이터로 지역 전체를 만들어 매달 갱신하고, "대표번호 없음" 트리거로 반경 조회합니다.
  6. 모든 테이블의 건물 키는 buildingRosterIdx와 건물관리번호로 맞춥니다.
  7. 업종 분류(role)가 "부동산" 분류 전체를 공인중개사로 보는 문제를 고칩니다.
  8. 비공식 호출 3곳과 데이터 저장 범위는 법무 확인 후에 진행합니다.
